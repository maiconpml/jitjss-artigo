\subsection{Finite Parameter Space Formalization}
\label{subsec:parameter_space}

To configure metaheuristics automatically using \texttt{irace}, we must convert the context-free grammar presented in Section~\ref{sec:design_space} into a finite parameter search space \citep{mascia2013grammars, mascia2014grammar, lopez2016irace}.
Because Backus-Naur Form (BNF) grammars can produce infinite derivation trees through recursive search structures or arbitrary operator sequences, automated algorithm configuration requires imposing structural bounds to enforce parameter finitude.

Following the methodology proposed by \citet{mascia2013grammars}, we bound recursive search structures by fixing the maximum recursion depth to 2 levels, creating parameter blocks for a primary search procedure and a secondary nested search procedure.
Crucially, to halt recursion definitively, the nested search procedure cannot select \texttt{ils}, restricting inner searches exclusively to non-recursive procedures (Local Search or Tabu Search).
Similarly, we limit multi-neighborhood search sequences in ILS to at most three distinct neighborhood structures, controlled by an integer parameter $\texttt{neighborhood\_number} \in \{1, 2, 3\}$.
Each active neighborhood slot $j \in \{1, 2, 3\}$ is associated with a categorical choice parameter (\texttt{neighborhood}$_{j}$) and an exploration mode parameter (\texttt{neighborhood\_exploration$_{j}$}), with the exception of the \texttt{relax} operator, which bypasses exploration modes.
Categorical decisions, such as initial solution generation, priority dispatching rules, and sequence schedulers, map directly to categorical parameters.
Numerical and ordinal parameters governing Tabu Search, including \texttt{tenure}, \texttt{elite\_list\_size}, \texttt{limit\_iters}, \texttt{max\_d}, \texttt{max\_c}, and \texttt{decrease\_divisor}, are defined as conditional parameters that activate only when TS is selected.
Furthermore, to control the trade-off between search intensification and diversification within Iterated Local Search, we introduced a dedicated numerical parameter (\texttt{max\_milli\_ils\_iteration} $\in [100, 30000]$) that limits the maximum duration of each ILS iteration in milliseconds.
This time-bounding parameter allows \texttt{irace} to prevent computationally expensive neighborhood explorations from consuming an excessive portion of the total execution budget.

In addition to conditional parameter logic, automated configuration can generate candidate algorithms that contain duplicate neighborhood choices within a sequence.
To prevent unpromising parameter redundancies, we implement a custom configuration repair script in R that intercepts every candidate algorithm generated by \texttt{irace} prior to execution.
The repair script identifies duplicate neighborhood choices within a sequence and replaces them dynamically with distinct, unselected valid neighborhood operators, ensuring that all evaluated algorithms maintain structural diversity.

\subsection{Automated Configuration Setup and Execution}
\label{subsec:irace_setup}

To prevent overfitting and ensure unbiased algorithm generalization, we generated a dedicated training set of 72 JITJSS instances for the \texttt{irace} configuration process, completely separate from the benchmark test instances of \citet{baptiste2008lagrangian}.
These training instances were generated following the exact structural patterns, distributions, and problem sizes as the standard benchmark instances.
Furthermore, to ensure that training instances were sufficiently challenging, we validated each candidate instance by running the CPLEX solver for 1 hour, discarding instances solved to provable optimality within that time limit.

To guide \texttt{irace} toward high-performing metaheuristic architectures on this training set, we established a total configuration budget of 25,000 algorithm evaluations.
Each candidate algorithm execution was subject to a maximum cutoff time of 60 seconds.
We executed \texttt{irace} in parallel using 6 execution threads to explore the design space efficiently.
To preserve deterministic execution time measurements across candidate algorithms, internal CPLEX calls within neighborhood operators (\texttt{relax}) and sequence timing sub-solvers (\texttt{cplex}) operated strictly in single-threaded mode (\texttt{threads=1}).

All algorithmic components and configuration interfaces were implemented in C++, and the complete solver codebase is publicly available in an open-source repository \citep{leles2026jitjss}.
We conducted the automated configuration experiments using the \texttt{irace} package version 4.4.3 \citep{lopez2016irace} running in the R environment.
All exact mathematical programming models and sub-problem relaxations were solved using IBM ILOG CPLEX Optimization Studio version 22.1.1.0 \citep{cplex22}.
To ensure reproducible and statistically sound pseudorandom number generation across parallel configuration runs, we integrated the PCG random number generator library \citep{oneill:pcg2014}.

All configuration and evaluation experiments were executed on a dedicated workstation equipped with an Intel Core i5-11300H processor (3.1 GHz base clock frequency) and 24 GB of RAM, running the Arch Linux operating system.
